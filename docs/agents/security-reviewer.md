## Project Context

**Repo:** `abofs/stonyx-oauth`
**Framework:** Authentication module for the Stonyx ecosystem
**Domain:** OAuth2 Authorization Code flow handling sensitive operations — client secret management, token exchange, session creation, and binding the OAuth2 `state` value to the user agent that started the flow (RFC 6749 §10.12, RFC 9700). Note the framing: `state` is CSRF protection **only** when it is bound to the requesting client; an unbound one-time token with a TTL is replay-window limiting, and treating it as CSRF protection was the defect fixed in #36.

## Tech Stack

| Layer | Technology |
|-------|-----------|
| Language | TypeScript (ES Modules) |
| Token Exchange | Native `fetch` (POST to provider token endpoints with client secrets) |
| Session Storage | In-memory `Map` (keyed by UUID session IDs) |
| CSRF Protection | **Requirement (RFC 6749 §10.12, RFC 9700):** the `state` value MUST be bound to the requesting user agent's authenticated state. A one-time token with a TTL and no binding is replay-window limiting, **not** CSRF protection. **Current implementation:** `oauth_state` `HttpOnly` cookie carrying a 32-byte `randomBytes` binding value; SHA-256 digest held server-side; constant-time compare; consumed on first presentation regardless of outcome. **Verify the binding, not the token.** |
| Auth Provider | Discord (built-in), extensible via `OAuthFlow` base class |

## Architecture Patterns

- **Client secret handling:** `clientSecret` is passed through provider config and sent in token exchange POST bodies — it is never logged but lives in memory for the lifetime of the process
- **State binding is the CSRF control — review the binding, not the token:** **Requirement (RFC 6749 §10.12, RFC 9700):** the `state` presented on the callback must prove that the callback came from the same user agent that started the flow. Single-use plus a 10-minute TTL does *not* establish that — it bounds the replay window only, and presenting it as CSRF protection is precisely the login-CSRF defect fixed in #36 (see the rationale comment at `src/main.ts:153-164`). **Current implementation:** `getAuthorizationUrl()` issues a `randomUUID()` state *and* a 32-byte `randomBytes(BINDING_VALUE_BYTES)` binding value, storing only `{ bindingHash, createdAt }` — never the binding value itself; `/login/:provider` sets that value as the `HttpOnly`, `SameSite=Lax`, `Path=/` `oauth_state` cookie (`Secure` derived from the configured redirect-URI scheme) and **fails closed** — the state is withdrawn via `discardState()` and the login rejected with 500 if the cookie cannot be set; `handleCallback()` deletes the record on recognition, *before* the TTL and binding checks, so the endpoint is not a repeatable oracle, rejects an empty candidate list rather than skipping the check, and constant-time compares every presented candidate via `OAuth.digestsMatch`. **A review that confirms only single-use and TTL passes a vulnerable design.**
- **Session ID is a live bearer credential — check how it is *delivered*, not only how it is validated:** After a successful OAuth callback a UUID session id authenticates every subsequent request via the `session-id` header (`src/auth-request.ts:104`, `:211`), and the session manager validates it against the in-memory `Map` with a TTL check. **Requirement:** a bearer credential must never travel in a URL. **Current implementation (#45, fixed — do not report it as present):** when `frontendCallbackUrl` is configured the callback redirects with a single-use, 60-second **exchange ticket in the URL fragment** (`src/auth-request.ts:189-193`), never the session id. The ticket is independent `randomBytes(32)` entropy, authenticates nothing at `GET /auth`, and is redeemed once at `POST /auth/session` (`src/auth-request.ts:230-237`). A fragment is not transmitted to any server, so `Referer` and access logs are out of scope for it; history and page scripts are not, which is what the single-use 60-second bound is for. **What to review here is whether that still holds** — a session id, or any value that authenticates or redeems, appearing anywhere in a redirect URL under any key is the defect. The suite's `assertNoCredentialInRedirect` / `assertNothingRedeemable` helpers (`test/integration/oauth-test.ts`) feed *every* query and fragment value to both surfaces for exactly this reason; a key-absence check (`notOk(get('sessionId'))`) does not establish it and has twice gone silently, permanently green in this repo.
- **The exchange endpoint is the module's one unauthenticated, attacker-reachable write surface:** `POST /auth/session` (`src/auth-request.ts:216-238`) takes an opaque ticket from an **unauthenticated** JSON body and returns a live session id. Its controls, all of which must survive any change: single-use, consumed *on recognition* before the TTL comparison so the route is never a repeatable oracle (`src/ticket-store.ts:113-121`); a 60-second TTL (`TICKET_TTL_MS`, `src/ticket-store.ts:12`); one indistinguishable `400` for unknown, spent, expired and unparseable alike. **Known residual, disclosed not fixed:** nothing binds a ticket to the client that started the flow, so a ticket observed inside its pre-exchange window is redeemable by the observer. Binding needs a cookie the cross-origin exchange cannot carry — blocked on `abofs/stonyx-rest-server#63` (CORS `credentials` is unsupported), **not** on `abofs/stonyx-rest-server#45`. Report a *regression* in the controls above; the unbound residual itself is already tracked and does not need re-reporting.
- **`TicketStore` stores the raw ticket, where `pendingStates` stores a digest:** `src/ticket-store.ts:95` uses the ticket itself as the `Map` key, a deliberate divergence from the #36 pattern (`{ bindingHash, createdAt }`, pinned by a unit test). Worth knowing when reviewing anything that serializes or logs module state. Marginal in practice — the record it keys also holds the plaintext `sessionId`, and `SessionManager.sessions` is already keyed by the plaintext session id — but it is a divergence, and no claim of digest storage is made for tickets anywhere.
- **Token exchange via fetch:** Code-for-token exchange uses `Content-Type: application/json` by default — some providers require `application/x-www-form-urlencoded`, which needs a provider-level `exchangeCode()` override

## Live Knowledge

- **Secret exposure risk:** `clientId` and `clientSecret` are stored as instance properties on `OAuthFlow` — any code that serializes or logs a provider instance could leak the secret; verify no toString/toJSON methods exist
- **Session fixation:** Sessions are created with `randomUUID()` and stored server-side — there is no session regeneration on privilege change, but since sessions are created fresh on each OAuth callback, fixation risk is limited to the session lifetime
- **Token storage:** Access tokens and refresh tokens are stored in the session Map alongside user data — if the session Map is ever serialized (e.g., for debugging), tokens would be exposed
- **No token revocation on logout:** `logout()` calls `sessionManager.destroy()` but does NOT revoke the access token at the provider — the access token remains valid until the provider's expiry; implement `revokeToken()` on providers for defense in depth
- **State token cleanup — two unswept maps, not one:** Expired records are only cleaned up when accessed, so stale entries accumulate indefinitely with no periodic cleanup, in **both** `OAuth.pendingStates` (`src/main.ts:58`, fed by an unauthenticated `GET /auth/login/:provider`, 600s TTL, holds a digest) and `TicketStore.tickets` (`src/ticket-store.ts`, reachable only after a successfully bound callback, 60s TTL, holds a **plaintext session id**). Tracked at `abofs/stonyx-oauth#43`, which names both sites — do not accept a fix that sweeps one
- **Redirect URI validation:** The `redirectUri` is set from config and used in both the authorization URL and token exchange — mismatches between configured and actual callback URLs cause silent token exchange failures; providers may also reject mismatches as a security measure
- **Open redirect potential:** If `frontendCallbackUrl` is configured, the callback handler redirects to that URL — carrying a single-use exchange ticket in the fragment on success (`src/auth-request.ts:193`), or `?error=...` on failure. The concern is unchanged and still live: ensure the configured URL is not user-controllable. Note the value carried is a ticket, not the session ID (#45); the redirect target itself is the risk here, not its payload. Also unvalidated: `${frontendCallbackUrl}#${params}` assumes the configured URL carries no existing fragment
- **Authorization header for user info:** User info is fetched with `Authorization: Bearer {accessToken}` — the access token is sent over HTTPS to the provider's user info endpoint; verify no HTTP fallback exists
